The portfolio will use rising planets, directional slides, and forming constellations to make the sections feel like a connected space journey. The selected approach extends the existing shared motion components and replaces the downward-driven project gallery with a native horizontal rail. This document specifies the proposed behavior for the engineering review; it does not authorize deployment.

## Problem and current behavior

The hero establishes the planetary visual reference. About and Experience already have gentle scroll and pointer movement, but lack deliberate arrival sequences. Skills has a reversible line-drawing effect. On larger desktop screens, Projects translates the row horizontally while visitors scroll down through a tall pinned section. Touch devices, short windows, and reduced motion currently receive vertically stacked projects.

The requested change is deliberate planet-style entrances, different sliding transitions between sections, and direct sideways exploration of Ideas in orbit.

## Decisions

- Use cinematic orbits. Each section has a distinct arrival direction and shares gentle physical settling, so the journey feels related to the hero.
- Extend the shared entrance system. Reuse Motion, Reveal, the existing easing and spring presets, and Lenis for the document; keep motion settings consistent without adding a library.
- Play entrances once per mounted section or project. Returning to a section leaves it settled and readable. Small decorative drift can continue.
- Preserve the portfolio content, color grading, artwork, links, and existing selection interactions. The current hero remains the visual reference.
- Keep Projects horizontal at every supported screen width, including reduced motion. Swipes, trackpads, keyboard navigation, and visible buttons provide access.
- Keep motion on decorative artwork and separate wrappers. Artwork labels, interest buttons, skill names, and their hit areas retain stable positions. Biography, noninteractive company labels, and role text may use short entrance slides without scale or blur. Gallery links remain in their natural card layout.

Local section animations were considered but not selected because repeated settings would be harder to keep consistent. A continuous flight-path guide was considered but not selected because it adds artwork and coordination beyond the requested section motion. An optional independent brainstorming opinion was declined.

## Section choreography

These values are proposed starting points for tuning in the real site, rather than claims about measured animation performance. Observe untransformed local artwork or text wrappers, rather than the height of an entire section. Trigger when the wrapper is visible by at least the smaller of 20 percent of its own height and 15 percent of viewport height. This remains reachable for tall content in short windows and at large zoom. The shared local entrance helper must check the actual visible height before latching entry, including the observer’s first callback; a numeric Motion viewport amount alone does not enforce this guard in the installed version. Recalculate the required visibility after wrapper or viewport size changes. Completion remains recorded after the entrance, focus, or reduced motion finishes it.

## Horizontal gallery behavior

Replace the pinned track and transformed row with one native overflow container. Use a flexible row, proximity snapping, responsive widths, and natural card heights. Start with cards around 60–65 percent of the desktop rail, capped near 44 rem, and around 86 percent of the mobile rail. These widths must leave a next-card preview without overflowing the document.

Actual horizontal scroll position is the single source for progress and the current-project count. Document scroll no longer determines the project's horizontal position. Measure each card's center relative to the rail and clamp its stop to the interval from zero to maximum horizontal overflow; use zero for the first stop and maximum overflow for the last. The current project is the nearest measured stop, with the earlier card winning a tie and explicit first/last selection within two pixels of either end. Progress represents actual horizontal distance divided by maximum overflow; if there is no overflow, hide that progress indicator.

Previous/next moves from the nearest current project. During an unfinished button-driven scroll, rapid presses advance from the last requested destination so they do not repeatedly request the same card. One Gallery-owned cancellation rule interrupts unfinished travel and clears the pending destination before direct touch, wheel, native page-key input, scrollbar dragging, focus correction, remeasurement, or live reduced-motion settlement. The next control press then starts from actual scroll position. Clear the pending destination when travel settles too. Identify each command so completion from an older command cannot clear a newer request. The rail's horizontal navigation keys use measured destinations like its buttons. Current count remains based on actual position rather than the requested destination.

```text
Swipe or trackpad --------> native horizontal scroll
Shift + wheel -----------> gallery horizontal movement
Buttons or rail keys ----> rail scrollTo
                                  |
                                  v
                            actual scrollLeft
                                  |
                         current card and progress

Ordinary vertical input -> existing page scrolling
```

- Keep ordinary vertical wheel input and vertical swipes available for travelling through the page. Horizontal containment must not contain vertical scrolling.
- Keep Lenis for the document. Mark the rail with `data-lenis-prevent-horizontal` so horizontally dominant gestures stay native. Installed Lenis 1.3.26 supports this attribute.
- Bypass Lenis for Shift+wheel within this rail. A single gallery handler normalizes pixel, line, and page wheel deltas, adjusts horizontal scroll, and prevents duplicate browser movement. It must not remap ordinary vertical wheel input. Return immediately for Ctrl-modified zoom events before remapping or preventing the browser default; use the same exclusion in the Lenis bypass predicate.
- Previous/next buttons move to the measured card stops. Disable them at the first and last project, accounting for the pending destination during rapid button presses. The rail itself supports Left/Right and Home/End while focused; project links retain normal keyboard behavior.
- Tab focus brings the project link into view. Any explicit correction changes only the rail's horizontal position; normal browser focus may also bring the project section into the document viewport.
- Gate each project's artwork entrance on both document visibility of the gallery and horizontal visibility of that card. A card must not consume its entrance while the entire gallery is offscreen.
- Recalculate stops after resize and font changes. Preserve the focused project when one is inside the rail; otherwise preserve the current project, then clamp to the new bounds. Avoid changing page position or selection state.
- With one project or no horizontal overflow, hide navigation and progress controls that cannot move anything. With no projects, show a readable empty message. No calculation may divide by zero.
- Keep project descriptions and links reachable in short windows and at 200 percent zoom. Use natural card height rather than a fixed viewport-height crop.

## Motion and interaction rules

Artwork entrance, existing scroll drift, and hover feedback must own different nested elements so their transforms do not overwrite one another. Reuse the existing motion presets, with a soft spring for decorative artwork and the existing ease-out curve for text. The durations above describe the intended visual pace; spring settling is tuned by its parameters.

For the Projects section, a noninteractive decorative frame supplies the short directional entrance; the rail's links, navigation controls, and scroll geometry stay in their final layout. Only decorative artwork within project cards rises or scales. This gives the rail a directional arrival without moving its interactive hit areas.

Turning reduced motion on immediately shows the final state of every entrance and marks it complete. Turning it off must not replay completed entrances or reset the interest, employer, skill, or gallery selections. Reduced motion also disables decorative drift and smooth programmatic gallery travel while preserving native horizontal access.

If focus reaches a control inside an unfinished reveal, finish that local reveal immediately. Decorative objects do not receive focus. Do not animate text scale, large blur filters, or fixed fullscreen overlays. Use motion values for continuous decorative changes; update React state only when the current project changes, not on every animation frame.

## Success checks

- About, Experience, Skills, and Projects have visibly different entrances with related settling and spacing. The hero remains the visual reference.
- Entrances play once, including after back-scrolling, keyboard focus, and live preference changes. Labels and focused controls stay readable during every entrance.
- The original biography, five interests, two employers, three roles, 29 skills, five projects, and existing links remain intact.
- Every project is reachable by horizontal swipe, trackpad, Shift+wheel, buttons, and keyboard. Ordinary vertical input still travels through the page, and wheel/pinch zoom over the rail keeps normal browser behavior even when Shift is held.
- Reduced motion preserves content and horizontal access with no entrance, drift, or smooth control animation. Toggling it preserves page and rail position and selections.
- Validate 320, 390, 768, 1024, and 1440 pixel widths, a 500 pixel tall window, 200 percent zoom, resized fonts, first/last cards, one/no-overflow projects, and an empty collection. Include an observed wrapper taller than five viewports to confirm the capped visibility trigger. The document has no unintended horizontal overflow or clipped descriptions.
- Check direct section navigation, rapid control presses, resize during gallery travel, focus on a previously hidden card, scrollbar dragging during travel, and reduced motion toggled during travel; stale completions must not clear newer requests. Progress and disabled states must match the actual rail position.
- Run the existing Vite build and browser checks. No test framework is currently configured; the engineering review must provide a browser verification plan rather than introduce a framework silently.
